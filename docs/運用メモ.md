最終更新: 2026-10-21

**このサイトの運用に、特定のPCは必要ありません。** 母艦は置かない方針です。

## 1. どこに何を置くか（この方針を崩さない）

```
GitHub            … コード・データ・履歴・自動実行          ← 中心はここ
パスワードマネージャー … APIキーの保管（読み出せる控え）
Google ドライブ     … 読み物・資料（この運用メモなど）
ブラウザ版Claude    … どの端末からでも指示を出す窓口
```

| 置くもの | 置き場所 | 理由 |
|---|---|---|
| コード・データ | GitHub | バージョン管理と自動実行が一体 |
| 毎日の自動更新 | GitHub Actions | 人間もPCも介在しない |
| 公開中のサイト | ロリポップ `/numbers/` | FTPで配信 |
| APIキー（実行用） | **GitHub Secrets** | CIがここから読む |
| APIキー（保管用） | **パスワードマネージャー** | GitHub Secretsは読み出せないので控えが要る |
| 読み物 | Google ドライブ | 共有しやすい |

### やってはいけないこと

- **APIキーをGoogle ドライブに平文で置かない。** 共有リンクの事故で金銭被害に直結する
- **リポジトリをGoogle ドライブの同期フォルダに置かない。** `.git` と同期が衝突して壊れる。
  バージョン管理はGitがやっているので二重に置く必要はない
- **会社の端末に個人のAPIキーを残さない。** 返却・初期化・IT管理が入ったときに面倒になる

## 2. 作業の始め方

### 2-1. どの端末からでも（推奨）

ブラウザで **claude.ai/code** を開き、GitHubの `webzeney/numbers3` をつなぐ。
インストール不要。スマホからでも指示を出せる。

最初のメッセージにこれを貼ると、前提を共有した状態で始められる。

> `webzeney/numbers3` のナンバーズ3検証サイトの作業を続けます。
> まず `docs/運用メモ.md` と `docs/仕様書.md` を読んでください。
> 公開済みの候補数字は絶対に変えないこと、選出バージョンは凍結されていることが最重要の制約です。

### 2-2. 手元のPCで動かしたいとき（任意）

ローカルで表示確認したい場合だけ。**常設する必要はない。**

```bash
git clone https://github.com/webzeney/numbers3.git
cd numbers3
python3 generate.py --no-ai      # APIキー無しで動く
python3 -m http.server 8765      # http://localhost:8765 で確認
```

- Python 3.12 で動かしている。**追加ライブラリは一切不要**（標準ライブラリのみ）
- `data/NUMBERS3_ALL.csv` と `data/sources/` は再配布しないため `.gitignore` 済み。
  clone直後は無いので、初回は `python3 generate.py` が取りに行く
- `file://` では動かない（fetchでJSONを読むため）。必ずサーバー経由で開く
- **ここで `git push` しないこと。** 本番は GitHub Actions が更新している。
  戻したいときは `git checkout -- data/`

### 2-3. APIキーを使って手元で試したいとき

3つのAI（AI予想・自動討論）を手元で動かす場合だけ必要。

```bash
cp .env.example .env
```

`.env` の3行にパスワードマネージャーから値を入れる。`.gitignore` 済みなのでGitHubには上がらない。
**作業が終わったら消してよい。** キーの正本はパスワードマネージャーにある。

## 4. 絶対に破ってはいけない約束

**4つとも実際に事故を起こした、または起こしかけた項目。**

### 4-1. 一度公開した候補数字は、絶対に変えない

`generate.py` の `main()` に、`data/rounds/<回号>.json` が既にあれば保存値で上書きする処理が入っている。
`candidates_ten` があれば位ごと方式、無ければ4数字方式と、**保存値で方式そのものも決める**。

> **事故（2026-10-02）**: 乱数の種に `LOGIC_VERSION` を入れていたため、表示上のバージョンを上げただけで
> 第7084回の候補が 1,3,5,9 → 0,5,7,8 → 2,4,5,6 と2回書き換わった。
> 対策として `SELECTION_VERSION` を分離・凍結し、スナップショットによるロックを入れた。

### 4-2. 選出バージョンは凍結する

```python
SELECTION_VERSION     = "2.1.0-tilted"   # 〜第7092回、第7098回〜
SELECTION_VERSION_POS = "3.0.0-pos3"     # 第7093〜7097回の5回のみ
POS_SWITCH_ROUND = 7093
POS_END_ROUND    = 7098
```

これらは**乱数の種に使われている**。値を変えると同じ回でも違う候補が出る。
方式を変えるときは、`LOGIC_VERSION`（表示用）ではなく**新しい定数を足して切り替え回を指定する**。既存の定数は書き換えない。

### 4-3. データが古ければ生成を止める（フェイルクローズ）

最新抽選日が5日以上前・回号の飛び・番号の形式不正などがあれば `DataError` を投げて停止する。
**前回値の流用も、勝手な補完もしない。**

### 4-4. 当たったことを「手法が良かった」と語らない

候補は210通りからのほぼ一様な抽選なので、的中は確率16%の事象が起きただけ。
`auto_debate.py` の `REFLECT_SYSTEM` に、AIがこれを書かないよう明示的な禁止条項を入れてある。

## 5. 日々の運用

### 自動更新（人間の操作は不要）

| cron (UTC) | JST | 用途 |
|---|---|---|
| `0 15 * * *` | 0:00 | 本命 |
| `0 1,3 * * *` | 10:00, 12:00 | 保険 |

1. `python3 generate.py --if-new`（終了コード 0=生成 / 2=データ異常 / 3=生成済み）
2. 差分があればコミット＆プッシュ
3. **終了コードに関わらず FTP でロリポップへアップロード**

データ取得元の公開時刻は実測で loto-life が抽選当日19:50、mk-mode が翌10:15。JST 0:00 には3時間以上の余裕がある。

### 手動でデプロイしたいとき

**プッシュだけではデプロイされない。** トリガーは `schedule` と `workflow_dispatch` のみ。

GitHub → Actions → 「ナンバーズ3 自動更新」→ 右上の **Run workflow** → main → Run workflow

### GitHub Secrets（設定済み・値はGitHub上にのみ存在）

`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY` / `FTP_HOST` / `FTP_USER` / `FTP_PASS`

### 既知の制約

使用中のGitHubトークンに `workflow` 権限が無く、**`.github/workflows/` 以下をプッシュできない**。
自動更新の設定を変える予定があるなら、トークンを作り直すときに `workflow` スコープを付ける。
（GitHub → Settings → Developer settings → Personal access tokens）

## 7. 現在の状態（2026-10-21）

### サイトの構成

```
このサイトは何をしているか   ← 定義ブロック（ページ最上部）
通算収支の台帳
01 第N回の候補
02 検証①：攻略本『別冊宝島271』の鉄則        ← 10項目。z値の解説はここに1回だけ
03 検証②：ネットの攻略サイトが言う手法        ← 12項目。黄金数字・コールドナンバー・曜日
04 3つのAIの予想
05 どう選んでいるか                          ← 選び方を変えた経緯の表もここ
06 この選び方は一様ランダムと何が違うのか
07 抽選の偏りの監視
08 AI同士の自動討論                          ← 討論ログ第1〜4回
09 登録した仮説                              ← p値の解説と、式の計算過程の実例
10 保存版ページ
```

### 検証の結論

**攻略本10項目＋攻略サイト12項目のうち、何も考えずに選ぶより当たりやすかった手法は0個。**

- 「裏数字26.1%」「後数字59.5%」は、**主張値そのものが基準（27.10% / 60.76%）より低い**
- 黄金数字は 選定期間12.15%（z=+4.69）→ **選定後9.99%（z=−0.03）**。後知恵の見本
- コールドナンバーは攻略サイト間で主張が正反対。実測ではご無沙汰の長さと無関係
- 曜日は金曜（主張された曜日）が基準どおりで、代わりに水曜が z=+2.01。多重比較の見本

### 選出方式の履歴

| 期間 | 方式 | 買い目 | 的中率 | 期待回収率 |
|---|---|---|---|---|
| 第7082〜7092回 | 4数字を両方の位に流用 | 16通り 3,200円 | 16% | 43.2% |
| 第7093〜7097回 | 十の位3 × 一の位3 | 9通り 1,800円 | 9% | 43.2% |
| **第7098回〜** | **4数字を両方の位に流用** | **16通り 3,200円** | **16%** | **43.2%** |

位ごと方式に変えたのは、ミニが2桁で決まるのに桁を区別していなかったため。
5回で戻したのは、3つのAIの討論（第4回）で2対1でA案が支持されたため。
**決め手は検証の速さ**で、的中率16%と9%では同じ精度に達するのに9%のほうが約1.9倍の回数が要る
（相対標準誤差 2.29/√n vs 3.18/√n）。期待回収率はどちらも43.2%で同じ。

### 実績

第7082回から15回判定済み。**的中1回 / 収支 −33,100円**。
なお**実際に購入しているわけではなく、買い目を毎回1口ずつ買ったと仮定した計算**。

### 気になっている数字

重み付け（`TILT_WEIGHT = 0.2`）に効果が確認できていない。

| 方式 | 重み0.2 | 一様 | 判定 |
|---|---|---|---|
| 4数字（現行） | 16.47% | 15.82% | z=+1.04 差なし |
| 位ごと | 8.62% | 9.49% | z=−1.78 差なし |

どちらも誤差の範囲。**効果が無いことがはっきりしたら `TILT_WEIGHT` を 0 にする。**

## 8. 過去の事故と対策

| 事故 | 原因 | 対策 |
|---|---|---|
| 公開済みの候補が2回書き換わった | 乱数の種に表示用バージョンを入れていた | `SELECTION_VERSION` を分離・凍結＋スナップショットロック |
| ベースCSSを2回破壊した | `index.html` を広い範囲でブロック置換した | **置換は必ず一意性を確認してから** |
| 保存版ページが全滅 | キー名を変えたのに旧キーを参照したままだった | 新旧どちらのキーでも動くフォールバック |
| AIが因果を語った | 所見のプロンプトが緩かった | `REFLECT_SYSTEM` に禁止条項を明記 |
| 無限ループ | 候補生成のループに上限が無かった | 回数上限＋フォールバック |
| PCで変な位置で改行 | `max-width:80ch` を入れていた | 削除 |

`index.html` を編集するときのルール：
1. Python で `assert s.count(old) == 1` を必ず付けてから置換する
2. CSS は既存ブロックを書き換えず、`</style>` の直前に追記する
3. 編集後に `<script>` 内のJSを `node --check` で構文チェックする
4. ローカルサーバーを立てて、デスクトップとモバイル両方で目視確認する
